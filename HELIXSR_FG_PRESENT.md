# HelixSR frame generation presented by OptiScaler

Goal: smooth HelixSR frame generation on non-NVIDIA GPUs. The frames are still generated by NVIDIA's DLSS-G core inside
helixsr.dll, but they are presented and paced by OptiScaler's FidelityFX frame-generation swapchain (the one FGOutput = fsrfg
uses) instead of the game's Streamline `sl.dlss_g`. On non-NVIDIA GPUs `sl.dlss_g` falls back to its CPU pacer. FF7 logs
"CPU pacer is skipping the frame because of timeout" and "Frame rate over 100ms, reseting frame timer", and players see
stutter.

Option: `OptiScaler.ini [HelixSR] FGPresent = auto | optiscaler | streamline`. For DLSS-G games the default (`auto`)
is the game's own Streamline (FGInput = nvngxfg), unchanged; `optiscaler` takes them to this route. Games without DLSS-G
get the OptiFG route (below) by default; `streamline` gives them OptiScaler's Streamline (FGOutput = dlssg) instead.

## Today's route (FGPresent = streamline)

```
game -> Streamline sl.dlss_g (fills the NGX DLSS-G parameter object, presents + CPU pacer)
     -> NGX EvaluateFeature(feature 11) -> OptiScaler Nvngx_FG (HUD cutoff) -> Nvngx_HelixSR -> helixsr.dll
     -> NVIDIA's core reads the parameters -> generated frame -> sl.dlss_g presents it
```

## Why we can't keep sl.dlss_g's own parameter object

`sl.dlss_g` (closed, NVIDIA) does three jobs in one place: it fills the parameter object, it calls Evaluate, and it
presents. It calls Evaluate from inside its own present hook, and it has no mode where someone else presents. If its
present hooks are switched off, it also stops filling parameters and stops calling Evaluate. If they stay on, it presents
and paces, which is the problem we want to remove. So "sl.dlss_g's parameter object" and "OptiScaler presents" can't both
hold.

## Chosen design (FGPresent = optiscaler)

```
game -> Streamline tags / constants / DLSSG options (the same data sl.dlss_g gets)
     -> OptiScaler FGInput = dlssg (Sl_Inputs; sl.dlss_g's swapchain hooks are already removed by OptiScaler)
     -> FGOutput = fsrfg: the FidelityFX FG swapchain presents and paces (FSR FG pacing, async, FramePacingTuning)
        frameGenerationCallback (FSRFG_Dx12::DispatchCallback) -> HelixSRPresent::Generate
          -> NGX DLSS-G parameter object (sl.dlss_g's keys and types) -> Nvngx_FG::D3D12_EvaluateFeature (same as today,
             including the HUD cutoff) -> helixsr.dll -> NVIDIA's core reads the parameters -> outputs[0]
```

What stays exactly the same:
- The generation path from `Nvngx_FG::D3D12_EvaluateFeature` down: the HUD-cutoff step, the Nvngx_DllProxy options,
  `helixsr.dll NVSDK_NGX_D3D12_EvaluateFeature`, `fg_evaluate` with menu detection, and NVIDIA's core reading the NGX
  parameters with NVIDIA's code. HelixSR's own front end and QuickFlow are not used.
- The data: the game's own `sl::Constants` (stored unchanged for each frame), the `DLSSGOptions` flags and dynamic
  resolution, the tagged depth / motion vectors / HUD-less / UI with their extents, and the backbuffer that contains the
  HUD.

What changes:
- Who writes the NGX keys: `OptiScaler/framegen/ffx/HelixSRPresent_Dx12.cpp` instead of sl.dlss_g. The key list and the
  setter types are the ones helixsr.dll reads from OptiScaler parameter objects (`kFgKeys` and the resources with
  `Subrect*` keys, which were recorded from games), checked against an FF7 dump with 121 keys. All values except two are
  copied straight from the game's data. The two that are not:
  - `MvecScaleX/Y` = Streamline's normalized `mvecScale` multiplied by the motion-vector extent. This is the same
    conversion OptiScaler uses for FSR FG. In the FF7 dump these are 856/480 at render size 856x480.
  - `ColorBuffersHDR` = HDR output is active, or the backbuffer is 10-bit or FP16 (FF7 dump: 1 with R10G10B10A2).
  - Constants taken as seen in the FF7 dump: `IsRecording=1`, `run_lowres_mvec_pass=1`, `Enable.OFA=1`,
    `EnableInterp=1`, `EvalFlags=0`, NoWarp and BidirectionalDistortionField subrects 0, `MultiFrame*=1`.
- Who presents and paces: the FidelityFX swapchain. It calls our callback with `presentColor` (the real frame with the
  HUD, which becomes `DLSSG.Backbuffer`) and `outputs[0]` (which becomes `DLSSG.OutputInterpolated`). `DLSSG.OutputReal`
  is a texture we own; it is always bound and never left null.

HUD and UI: `DLSSG.HUDLess` and `DLSSG.UI` are the game's tagged images, handled the same way as today. NVIDIA's core does
the HUD handling. On the FFX side, no UI resource is registered with the swapchain, `FGDrawUIOverFG` is ignored, the
FSR HUD-copy / hudless-compare step is skipped, and reprojection is forced off. So there is no second UI pass. If the
game has been tagging HUD-less or UI images and one is missing for a frame, that frame is not generated and the real
frame is shown instead. Its HUD is never generated without the HUD-less image.

States: inputs go to `NON_PIXEL_SHADER_RESOURCE` and the output to `UNORDERED_ACCESS`, then back after the call. These
match the states Nvngx_FG assumes for Streamline today. The HUD-less image is put in `COPY_DEST` when the HUD cutoff is
active, because that is what Nvngx_FG's HudCopy expects. If something is missing or Evaluate fails, the callback copies
the real frame into `outputs[0]`, so the swapchain never presents an image that was never written.

The NGX feature is created on the swapchain's command list on first use (sl.dlss_g's creation keys), and recreated when
the backbuffer size or format changes. Old handles and textures are released `BUFFER_COUNT+4` frames later. NGX init
goes through `Nvngx_FG::D3D12_Init_Ext` when the FSR FG objects are created. helixsr.dll counts inits, so the game's
own NGX init is harmless. Threading: everything runs on the FidelityFX present thread, the same thread sl.dlss_g used.
It works on the direct queue and on the async compute queue (`FGAsync`); helixsr.dll supports both list types. FSR's
cheap "prepare" dispatch still runs and its output is unused.

Config wiring: if `FGPresent = optiscaler`, the game has sl.dlss_g, and the user hasn't set `FGInput`, HelixSR.cpp sets
`FGInput = dlssg` and `FGOutput = fsrfg` as volatile values. dllmain keeps `FGNvngxReplacement = HelixSR` for that
combination.

## helixsr.dll: no new export needed

The existing `NVSDK_NGX_D3D12_Init_Ext`, `CreateFeature(11)` and `EvaluateFeature` with an OptiScaler parameter object
already do everything (`foreign_params` / `import_foreign` read `kFgKeys`). Evaluate records on whatever command list it
is given, direct or compute. No closed-source change is needed.

Optional, for checking: helixsr.dll already prints all evaluate parameters with `[FrameGeneration] Log = 1`
(`ngx_param_dump`, first two frames). That dump is the equivalence gate below.

## Other FG inputs: the OptiFG route

Games without DLSS-G (FSR 3.1 frame generation: FGInput = fsrfg; FSR 3.0: fsrfg30; XeSS: xefg; none: upscaler, with
the HUD fix) use the same `HelixSRPresent::Generate` on the FSR FG swapchain (FGOutput = fsrfg, FGNvngxReplacement =
HelixSR, set by `HelixSRFgRoute.h` when OptiScaler.ini leaves them on auto). These inputs have no Streamline data:

- Constants: `IFGFeature::FillDlssgConstants`, the code OptiScaler's DLSSG output uses to send Streamline constants
  from the same input values (near / far ordered, a projection from the vertical FOV and aspect ratio with a reverse-Z
  one for inverted depth, identity reprojection matrices, the camera vectors when given, jitter, mvecScale normalized
  by the motion-vector size, reset, depth inverted, dilated / jittered motion vectors). `MvecScaleX/Y` is then the
  input's pixel scale again.
- Images: the input's depth and motion vectors; its HUD-less image (the game's, the one OptiScaler captures around the
  game's FSR present callback, or the HUD fix's) and UI image when there is one, under the same rule as above (once
  seen, a frame without it shows the real frame).
- No DLSS-G options: no dynamic-resolution size (InternalWidth/Height = depth size), no menu detection.
  `ColorBuffersHDR` also follows the input's HDR flag. `DrawUIOverFG` stays usable (it draws into the real frame).

A game with both DLSS-G and FSR frame generation stays on the DLSS-G route (the folder scan decides); for its FSR frame
generation set `[FrameGen] FGInput = fsrfg` and switch FSR frame generation on in the game.

## Test plan (main session, FF7 Rebirth, HelixSR Scaler, quiet system)

1. **Parameter gate (no FPS run).** In `helixsr.ini` set `[FrameGeneration] Log = 1`. Run with `FGPresent = streamline`
   and save the `fg: evaluate parameters` dump. Repeat with `FGPresent = optiscaler`. Compare the two dumps: the same keys
   and slots; the same Depth/MVecs/HUDLess/UI sizes and formats; the same subrects; the same InternalWidth/Height,
   MvecScale, ColorBuffersHDR and DepthInverted; camera values in the same range. Any difference: stop and fix
   `HelixSRPresent_Dx12.cpp`.
2. **Image check.** Same spot and HUD visible, with `FGPresent=optiscaler`: no HUD wobble or ghosting; menus show real
   frames (menu detection); no flashing on camera cuts (reset).
3. **Frame times, 60 s each, same save/spot, PresentMon (or MangoHud frametime log):**
   a. FG off.
   b. FGPresent = streamline (today).
   c. FGPresent = optiscaler, with FGAsync off.
   d. Optional: c with FGAsync on.
   Compare average FPS, 1% / 0.1% lows, frame-time standard deviation, and the share of frames more than 2x the median.
   Check the log for "CPU pacer" lines (expected to be gone in c) and for "HelixSR FG present" errors.
4. Pass criteria for making optiscaler the default: gate 1 identical, image identical by eye, and c has better lows and
   standard deviation than b at a similar average.

## Risks

- The parameter mapping can differ from sl.dlss_g in details we can't see: matrix conventions, MvecScale, ColorBuffersHDR,
  dynamic-resolution internal size. Gate 1 catches these before anyone judges image quality.
- Hudless format transfer: when the HUD-less format differs from the swapchain format, OptiScaler gives a converted
  copy. In FF7 the formats are the same.
- Latency: there is no Reflex frame pacing from sl.dlss_g. The FSR FG swapchain uses OptiScaler's latency options
  (AntiLag 2 / fakenvapi / XeLL).
- FidelityFX's own `reset` (a frame-id gap) is ORed with the game's reset, which may cause more resets than
  sl.dlss_g would.
- Not built or run on a GPU here: the first in-game run is also the first runtime test.
